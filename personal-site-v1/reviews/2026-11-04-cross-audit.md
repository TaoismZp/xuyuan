# 交叉审计：个人长文网站 × 许愿式交付 v7.5（2026-11-04）

**范围**：本公开仓库中已锁定的 v7.5、Vision v2、Blueprint v2、作者写作页源码、writer E2E、PROJECT_STATE 与 recovery 状态。站长本人已登录 GitHub 的真实发文尚未测试。没有直接访问站长 iPad 的已登录浏览器，也没有使用不可访问的原始本机苏格拉底 Skill 文件，故不声称完成了该 Skill 的逐条原文调用。

## 一、苏格拉底式审题（六类问题，不把质疑预设成答案）

| 问题 | 实际判断 | 证据或反证 |
| --- | --- | --- |
| 概念：什么是“网站完成”？ | 不是静态页面可打开，而是已有文章可读、作者可持续发布与迁移 | Vision 与 User Job 不同；PROJECT_STATE 仍为 PENDING_OWNER |
| 假设：真的需要重型 CMS 吗？ | 不一定；作者已在外部完成长文写作，MVP 可只接受 Markdown | token-free writer 的备选流程已存在 |
| 证据：技术 PASS 能否推导用户通过？ | 不能；Browser CI 不能模拟站长 GitHub 登录和现实切换页面 | AUTHOR_GIT_COMMIT / PUBLIC_PAGES_POST_UPDATE 待验收 |
| 视角：读者与作者各要什么？ | 读者要可靠安静的阅读；作者要简单发文与拥有内容 | 用户选择的极简 Vision 已锁定；不应回到交易终端 |
| 后果：最大的失败是什么？ | 初版还未使用就因为更多配置和解释被放弃，或草稿误公开 | 公共仓库、Token/CMS 复杂度、编辑器不自动保存 |
| 反思：该先优化页面还是验证闭环？ | 优先校正无 Token 发文流程中的阻断，再执行真实站长验收 | 小改动可回滚，不重做首页 |

## 二、精英思维：主工具「状态转移/瓶颈」，补充「古德哈特」「选择偏差」「信息价值」

- **状态链**：有成稿 → 整理 Markdown → 人工复制 → GitHub 原生 Commit → Pages → 读者打开。
- **发现的可证伪缺陷**：旧 writer 在用户只填好内容、尚未点击“复制”时，仍可点 GitHub；链接仅预填文件名，不带正文。用户可能在 GitHub 得到空白新文件。这是发布漏斗中的可修故障，并非要求增加复杂 CMS。
- **古德哈特**：完善四件套、CI PASS、恢复文件数目是良好的过程代理，但不能代替真实作者发布与读者阅读。
- **选择偏差**：熟悉 GitHub 的自动化测试者与只用 iPad 的作者不等价；这项风险不能靠复述测试日志消除。
- **信息价值**：当前最有价值的下一条新证据，不是再重绘首页，而是一次作者真实粘贴提交。一次失败的具体步骤比一份抽象升级计划更有信息增量。

## 三、整改矩阵（保持原稿及视觉约束）

| 优先级 | 问题 | 本轮处理 | 验收 |
| --- | --- | --- | --- |
| A | 未复制文章也能跳 GitHub，误以为正文随 URL 自动转移 | 禁止提前跳转；复制成功才允许。手动复制失败的降级路线需明确确认 | E2E 检查提前点击被阻止、复制后解锁、再次改稿重新锁定 |
| A | 工程 PASS 被误当真实作者发文 PASS | 保留 owner PENDING，不擅改 state 的历史 release commit | OWNER_ACCEPTANCE 与 state 保持待本人实测 |
| B | 过程没有先检验“不造网站”的更轻方案 | v7.6 候选 Gate 0 + 对照基线 | 后续一个项目试验，不直接升级锁定规范 |
| B | 长期维护/自我更新缺位 | 候选 Gate 7，记录使用摩擦、资产可迁移性 | 站长真实下一篇文章 |
| C | 编辑器刷新丢稿 | 当前设计是“已完成成稿的导入/发布助手”，明确无自动保存并提供 .md 导出；不擅自暗开本地存储 | 当前保留；真实作者如在站内写初稿再考虑 opt-in 草稿恢复 |
| C | 站点和游戏混用公开 `xuyuan` 仓库、地址长 | 未来可选独立仓库/域名，但此时迁移风险比收益更大 | 暂不搬迁，先验实际发文 |

## 结论与否决条件
本轮不重设计首页、不新增 CMS、不申请 GitHub Token、不写虚构测试长文、不碰用户原始稿件。实际代码改动只改善 GitHub handoff 的真实性；作者登录/实际发布依旧 PENDING。新 CI 失败则当前候选不能合并。若真实站长发表仍困难，返回产品目标与更轻发布方式的比较，而不是继续堆文档。
