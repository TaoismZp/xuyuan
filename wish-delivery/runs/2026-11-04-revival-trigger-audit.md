# 「断档重生」自审与验收记录 — 2026-11-04

本记录与上轮 v7.8-RC1 的 Vision/Blueprint/自我监理连用；本轮新增的是跨聊天**调用语义与可验证的路由行为**，不改正式 v7.6 与 v7.7 草案。

## Vision / 交付目标
一句「断档重生」，在一个可以回复的新聊天中恢复本项目/讨论的**最近可信状态**，识别下一步后继续，而不是让用户重新讲历史。无需声称自动修复 ChatGPT 旧对话或恢复未归档的逐字聊天。

## Blueprint / 关键执行链
用户短语 → 本线程唯一主题或显式主题 → 私密索引（项目 + 重要讨论）→ 原始 RECOVERY/STATE/稿件 → 独立核验身份/产物/权限 → 安全续做 → 新检查点 → 回读。

必须区分有当前上下文的聊天、全新聊天裸短语、全新聊天明确主题三种不同入口。允许只追问**项目名字**，禁止反问用户重复旧需求。不能拿“最新修改时间”冒充用户意图。

## 实现和审查边界
- 通用公开规则：`wish-delivery/recovery/REVIVAL.md`
- 决策路由：`wish-delivery/recovery/revival-router.mjs`，无联网/ChatGPT 数据读取能力。
- 28 个合成对抗案例：误触发、明确主题、昵称冲突、无上下文多项目、无索引、无原稿、旧对话已终止、身份错绑、用户授权门槛、隐私、真实下一动作。
- GitHub workflow：`.github/workflows/wish-revival.yml`；同一 SHA 的主分支检查保留。
- 私有 ChatGPT Library 索引另行保存；公开 GitHub 不存用户聊天文本或未公开稿件。

## 主要反例
1. 全新聊天输入裸短语，但网站、书稿等多个项目仍未完成 → **CHOOSE_TOPIC**，不能自信误接班。
2. 只有一条索引 → **VERIFY_CHECKPOINT**，不能直接给 PASS。
3. 旧会话文本已丢失但有项目 Git 提交 → **可以恢复已提交的工作**，不能凭空补回所有消息。
4. 已终止项目 → **TERMINAL**，没有用户重启授权不得复活。
5. 只有 CI 成功但必须本人发文 → **PENDING_OWNER**，不能宣称全局完成。
6. 文件缺失或版本冲突 → **BLOCKED_CONTEXT / VERIFY_EVIDENCE**，不得伪造恢复。

## Independent supervision
当前的合成路由与审查由同一执行环境制作，属于**自审 + CI**，不构成用户新聊天的真正异质独立验收。

## Reality Gates
- GitHub 代码及合成测试：按实际 CI 结果填写，不能预填 PASS。
- 账号全局自定义指令已安装：**UNVERIFIED**；需用户在设置里一次性粘贴。
- 新对话完全冷启动：**PENDING_REAL_TRIAL**。
- 24/7 自动备份所有聊天：**UNSUPPORTED**。
- ChatGPT 平台故障修复：**OUT_OF_SCOPE**。

唯一下一步：先验证 CI + 私密恢复中心回读；让新对话仅输入「断档重生」检验实际路由，并在不同主题/旧项目上跑实战接班。
