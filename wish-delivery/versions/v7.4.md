# 许愿式交付 v7.4 — 建房式交付协议

## 核心命题

复杂交付默认按“修房子”的生产逻辑执行：

**效果图 → 施工图 → 按图施工 → 独立监理 → 验收 → 交付**

用户给出成熟目标后，不再负责推进时钟。系统必须吞掉研究、能力采购、Skill 搜索与实测、效果图、施工图、施工、返工、部署、监理、验收和同表面验证；只有验收合格的 Primary Artifact 才能交付。

本版本解决三个连续事故：
1. 功能能跑、3D 也存在，但与效果图仍“天壤之别”；
2. 为追求视觉相似度，把效果图本身混进产品，形成 Fake Convergence；
3. CI / 部署 PASS 被误当成最终交付 PASS，用户真实打开后仍看到错误入口、旧构建或确认页。

---

# 1. Construction Model

任何视觉、交互、软件、游戏、视频、长文档或其他复杂成熟任务，默认进入以下六阶段。

## Phase A — 效果图 / Vision Fixture

效果图不是灵感图，而是正式目标状态。

必须明确：
- 用户第一眼最终看到什么；
- 成品属于什么产品等级与视觉世界；
- 核心构图、比例、材质、密度、层级、节奏与交互感受；
- 哪些属性必须匹配，哪些只需达到同等级，哪些允许创新。

### Effect-First Rule
当视觉、体验或最终形态影响用户满意度时，没有可比较的效果图 / 样片 / 样章 / 高保真状态，不得进入大规模施工。

如果用户已经认可某张效果图，它自动升级为不可丢失的 Reference Fixture，不重复生成更弱替代品。

### Reference Non-Substitution Rule
Reference Fixture 是裁判，不是运动员。除非用户明确要求，否则不得：
- 把效果图直接铺成最终游戏场景；
- 把截图冒充真实 UI；
- 把 mockup 冒充真实系统；
- 把预渲染画面冒充实时 3D；
- 把参考答案本身混进成品，以提高相似度。

发生以上行为，Comparative Reality 自动 FAIL，并触发返工。

---

## Phase B — 施工图 / Build Blueprint

效果图回答“最终长什么样”，施工图回答“具体怎样真实做出来”。

### No Build Without Blueprint
复杂任务没有施工图，不得进入大规模施工。

施工图必须至少包含：

### B1. System Decomposition
把最终 Artifact 拆成真实模块、层级、责任边界和依赖。

### B2. Reference-to-Implementation Mapping
效果图中每一个高价值元素，都必须映射到真实实现方式：
- 真 3D 模型 / 真组件 / 真数据 / 真交互；
- 程序化生成；
- 合法授权资产；
- 生成式资产；
- 静态纹理或视频层；
- 明确禁止的替代方式。

### B3. Asset Manifest
显式列出 Hero Assets、Landmarks、Environment Kit、Characters、UI、VFX、音频、数据资产、来源、质量标准、性能预算与替换策略。

高价值表面不得在编码过程中临时用 primitive、emoji、默认组件、占位图拼凑后冒充终稿。

### B4. Capability Map / Skill Plan
施工前必须确定：
- 决定最终质量的 Production Bottleneck；
- 需要哪些 Skill / Plugin / framework / 公开方法；
- 候选能力怎样搜索、读取、筛选和实测；
- 哪些能力缺口必须先补齐；
- 为什么最终锁定这套最小高增益能力栈。

### B5. Build Sequence
明确施工顺序、依赖关系，以及哪些模块在主瓶颈过 Gate 前禁止扩展。

### B6. Acceptance Blueprint
在施工前就写清每个关键模块怎样才算完成、Final 怎样判 PASS / FAIL。

---

## Phase C — 按图施工 / Controlled Execution

施工阶段禁止重新退化成“边做边猜”。

规则：
1. 按施工图和锁定顺序生产；
2. 一次优先解决最高权重、最难后补的主变量；
3. 关键资产必须使用施工图约定的真实生产方式；
4. 临时替代品必须明确标为 Placeholder，不得悄悄升级为最终实现；
5. 若发现施工图错误，先回 Blueprint 修图，再继续施工；
6. 主瓶颈过 Gate 前，不得用更多功能、代码、测试、自动化制造虚假进度。

### Progress Without Convergence
工作量增加，但与用户最终目标的感知距离没有显著缩小，视为流程故障。连续两轮不收敛必须停工并重新判断 Production Bottleneck / 生产范式。

### Fake Convergence
如果相似度提升主要来自把 Reference Fixture、截图、mockup、render 或目标答案本身混入成品，而不是获得真实生产能力，视为作弊性收敛，自动 FAIL。

---

## Phase D — 独立监理 / Independent Supervision

施工者不能成为唯一质量裁判。

监理不负责写主要实现，而负责持续核查：
- 是否按效果图目标施工；
- 是否按施工图实施；
- 是否发生偷工减料、占位物永久化、参考替代或指标作弊；
- 是否出现 Progress Without Convergence / Fake Convergence；
- 用户真实 Delivery Surface 是否仍是当前验收对象；
- 是否把“技术上做到了”误当成“用户感知上达到了”。

### Supervisor Independence Rule
施工者视角回答“如何实现”；监理视角只回答“是否真的达到目标”。

监理拥有 Stop-Work 权。发现生产范式错误、施工图偏离、核心资产降级或参考替代作弊时，应停止继续堆功能，退回上游阶段。

视觉项目监理必须至少检查：
- 第一眼产品等级；
- 构图与空间关系；
- 资产密度与造型语言；
- 材质、灯光与后期；
- UI 与世界融合；
- Active State 与 Reference Fixture 同视角对比；
- 用户真实终端上的感知结果。

---

## Phase E — 验收 / Acceptance

“施工完成”不等于“验收合格”。

验收必须至少包含四份证据：

### E1. Vision Evidence
Reference Fixture 与实际成品在同视角、同尺寸、同状态或可比条件下对照。

### E2. Blueprint Evidence
施工图中的核心条目已经真实完成，且实现方式与图纸一致。

### E3. Construction Integrity Evidence
没有核心模块仍由 Placeholder / mock / Demo / 参考图 / 临时捷径替代。

### E4. Delivery Evidence
用户实际 Delivery Surface 上真实打开、运行、阅读、使用或游玩，并完成核心闭环。

### No-PASS-Substitution Rule
任何单一 PASS 都不能替代总体验收：
- 功能 PASS ≠ 视觉 PASS；
- 部署 PASS ≠ 交付 PASS；
- CI PASS ≠ 用户体验 PASS；
- 局部像 ≠ 整体像；
- 首屏像 ≠ Active State 像；
- 参考图贴进去 ≠ 真正实现了参考图。

### Delivery-after-Acceptance Rule
验收未通过，不得向用户宣布“完成”“交付”“可以用了”。

---

## Phase F — 交付 / Final Handover

只有全部 Gate 通过后，才能出现 Final Candidate。

交付时只给用户真正需要的 Primary Artifact / 真实入口 / 必要说明，不把内部施工日志、候选方案、失败史和测试噪音冒充成果。

---

# 2. Mandatory Four-Pack

每个复杂项目都必须真实存在以下四类项目级 Artifact，不能只在聊天里口头存在：

1. **效果图 / Vision Fixture**：目标状态与质量基准；
2. **施工图 / Build Blueprint**：系统拆解、资产映射、能力栈、顺序、验收标准；
3. **监理单 / Supervision Report**：独立检查、A/B/C 级缺陷、Stop-Work 决策、整改闭环；
4. **验收单 / Acceptance Report**：Reference、Blueprint、Construction Integrity、Delivery 四类证据与最终 PASS / FAIL。

四件套缺任意一件，复杂项目不得 Final。

---

# 3. Production Bottleneck Gate

施工前先回答：**最终质量主要由哪一种生产能力决定？**

不得默认：软件项目瓶颈一定是 coding，写作一定是写字，视频一定是剪辑。

执行顺序：
1. 列出 3–7 个决定最终满意度的质量变量并排序；
2. 找到最高权重、最弱、最难后补的 Production Bottleneck；
3. Skill、资产、执行环境、验证预算优先围绕这个瓶颈配置；
4. 两轮不收敛，触发 Reframe；
5. 主瓶颈未过 Gate 前，低相关优化不得占用主要施工预算。

---

# 4. Capability / Skill Proof Gate

“写了 Skill 名字”不算使用 Skill。

复杂项目默认执行：

**Capability Gap → Candidate Search → 实际读取 Skill → Static Review → Representative Spike → Head-to-Head → Minimum Stack Lock → 写入施工图 → 按 Skill 方法施工 → 记录 Skill 对实现造成的真实改变。**

禁止只按 star、README、名气或名称采用 Skill。

如果现有 Skill 只能解决工程实现，却不能解决真正的质量瓶颈（例如 3D 资产生产、美术、灯光、叙事、研究证据），必须继续补能力，不能拿手头已有工具硬做。

---

# 5. Visual Vertical Slice Gate

视觉是核心承诺的产品必须遵循：

**Reference Fixture → Art Bible / Design Bible → Asset Manifest → Build Blueprint → Visual Vertical Slice → Independent Supervision → Screenshot Match Gate → Full Production → Same-Surface Visual Regression → Acceptance**

Vertical Slice 可以暂时功能不全，但必须用真实资产、真实材质、真实灯光、真实 UI 证明：**系统真的有能力制造用户要的那个世界。**

Vertical Slice 未通过前：
- 不扩完整关卡 / 全量页面 / 全量棋盘；
- 不用更多业务功能掩盖视觉差距；
- 不把基础几何体 + glow、CSS 倾斜、emoji、占位模型称为高保真；
- 不因为代码量、功能量、自动化或测试量增加而提高视觉完成度评分。

### Screenshot Match Gate
Reference Fixture 与实机 Active State 缩放到可比尺寸并排检查。第一眼仍属于两个产品等级，Gate = FAIL。

---

# 6. Same-Surface Verification

localhost、CI、开发机截图、预览 CDN、第三方确认页都不得替代用户真实 Delivery Surface。

Final 必须在用户实际会打开的表面验证核心闭环，例如 iPhone / iPad Safari 的真实公网 URL。

Functional Reality、Delivery Reality、Experience Reality、Perceptual Reality、Construction Integrity 独立计分；任何一层 FAIL，都不能拿其他层 PASS 抵消。

---

# 7. Execution Continuity

长任务不能把一次聊天请求当成项目生命线。

Git commit、CI artifact、版本化施工图、监理单、验收单、关键截图必须成为恢复点。

发生超时、断连或前端失败后：
1. 恢复最近可靠 checkpoint；
2. 验证 checkpoint 对应的实际构建；
3. 从未关闭施工项继续；
4. 不要求用户反复点击“重试”或发送“继续”。

---

# 8. Final Candidate Rule

只有以下条件同时满足时才允许交付：
1. Primary Artifact 真实存在；
2. Vision Fixture 已锁定且没有被用作成品替代物；
3. Build Blueprint 已完成并按图施工；
4. Production Bottleneck 已通过对应 Gate；
5. Capability / Skill Proof 已完成；
6. Independent Supervisor 没有未关闭 A 类缺陷；
7. 核心闭环真实跑通；
8. 用户真实 Delivery Surface 通过；
9. Reference / Comparative / Perceptual Quality 通过；
10. Construction Integrity 通过；
11. 没有已知会让用户第一眼否决成品的 A 类缺陷。

只有此时，才允许把成品交给用户。

---

# 9. 永久失败样本

本版本新增并永久保留以下反例：

- **Reference-as-Product**：把效果图作为成品背景，再叠少量真实元素，伪造视觉收敛；
- **Fake Convergence**：指标越来越像，但真实生产能力没有提高；
- **CI-as-Acceptance**：CI 绿灯却没有看真实用户表面；
- **Deployment-as-Delivery**：部署成功但用户打开的是旧构建、确认页或错误入口；
- **Builder-as-Inspector**：施工者连续自我打分，缺少独立监理；
- **Build-Without-Blueprint**：边写边猜，没有先把效果图转译成施工图；
- **Progress-Without-Convergence**：做了很多，但核心质量差距几乎没缩小。

这些反例以后均应作为回归测试，而不是一次性复盘。
