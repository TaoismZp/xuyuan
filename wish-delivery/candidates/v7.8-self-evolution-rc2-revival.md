# 许愿式交付 v7.8-RC2（候选）— 「断档重生」跨对话接班

状态：**CANDIDATE / NOT ACTIVE**。继承 v7.8-RC1；生效版依旧以 `wish-delivery/CURRENT.json` 指向的 v7.6 为准，旧规范不改写。此扩展是 **Recovery Trigger / Invocation Contract**，不能等同 ChatGPT 平台级自动恢复或聊天记录备份。

## 用户意图和真实交付面

用户在任何**可正常使用的** ChatGPT 对话发送独立短语「断档重生」，即可请求执行跨对话项目/重要讨论恢复，而不是要求重新介绍过去的背景。支持「断档重生：个人网站」等带主题形式。实际交付面包含：

- 可恢复外部档案：私密文件库 `/跨对话恢复中心/README.md`、`PROJECT_REGISTRY.json`、`THREAD_REGISTRY.json`；项目独立 RECOVERY/STATE/原始产物。
- 通用行为入口：账号自定义指令（需用户自行启用；保存文件不等于已安装）；当前聊天若已有明确主题，也可直接触发。
- 通用执行协议及回归样例：`wish-delivery/recovery/REVIVAL.md`、`revival-router.mjs`、`test-revival.mjs`。

## 触发后：定位 → 验证 → 接力，不把用户当项目经理

1. **识别上下文**：带项目名的指令优先；否则依据本对话明确的最后未完主题；新对话则搜索私密注册表、最近可靠 checkpoint 与已授权原始来源。仅命中唯一的、证据充分的主题才自动选定。
2. **消解歧义**：存在两个以上等可能项目、找不到具有证据的唯一主题时，仅问「你要接替哪个：A / B？」或展示可点选候选；不让用户重复旧需求、历史过程或已保存资料。
3. **读取检查点**：按原始目标、最后已核验成果、版本/哈希、未完成项、唯一下一步读取；比对 GitHub、Library、构建、网页等真实产物。注册表和记忆只提供线索，不提供 PASS。
4. **立即执行可安全执行的下一步**；必须用户本人登录、支付、发布、泄露隐私或不可逆行动时标记 PENDING_OWNER，不替代本人授权；已终止/完成项目不暗中重启。
5. **新证据即归档**：产物、变更矩阵、PASS/PENDING/UNVERIFIED、下一步写回适当权限的外部档案；写后重新读取。若不可写，明确「尚未归档」并提供可保存交接卡。公开 GitHub 不允许完整对话、私密草稿、密码、Token 或私人路径。

## 与断档故障的现实边界

- **旧聊天无法回复时**，用户须在可用的新聊天发送短语；不能让已损坏的窗口恢复响应。
- 不能保证每条旧聊天已有检查点，也不能自动抓取所有过去对话；逐条记录仍需账号数据导出，缺失资料不得杜撰。
- 新聊天无法凭裸短语断定是哪条旧聊天；同时多个活跃项目时需要最小选择。
- 没有活跃 ChatGPT 会话或已建立的 Automation，不承诺后台执行或持续抓取。
- 所谓「所有对话」指全局自定义指令启用后的**通用触发约定**及有权限的恢复流程，不是模型跨会话的魔法记忆。
- 不在本文件擅自覆盖已生效 v7.6，不根据合成测试自动晋级。

## 成功标准和否决样本

触发能命中、歧义不会乱选、缺检查点不捏造、读取后能执行一步、无法执行时指出真正阻塞。机械用例通过只证明路由逻辑；需新的独立聊天冷启动、一个真实项目与一个非项目主题的恢复测试才有资格申报普遍有效。独立审查与实际跨项目质量提升仍 PENDING。
